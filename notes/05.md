# D5 学习笔记

## 一、pytest 基础

### pytest 是什么

Python 最常用的测试框架。规则：

- 文件名 `test_*.py`
- 函数名 `test_*`
- 运行时自动发现并执行

### assert 是什么

```python
assert 条件, "失败时的提示"
```

- 条件 `True` → 通过
- 条件 `False` → 抛 `AssertionError` → pytest 标红 FAILED

**和 `if` 的区别**：`if` 是正常分支，`assert` 是"我断定这里必须成立"。**测试文件只用 `assert`，不用 `if`**。

### is vs ==

- `==` 比较**值**，`is` 比较**对象身份**
- `1 == True` 是 `True`，`1 is True` 是 `False`
- **测 bool 用 `is`**：能抓住"函数返回 1 而不是 True"的手滑（`1 == True` 会过，`1 is True` 会挂）
- 测其它类型用 `==`

### -v 是什么

`-v` = verbose，显示每个测试的**完整名字 + 结果**。不带 `-v` 只显示 `..........`，看不出哪个挂了。

**常用组合**：

| 命令 | 作用 |
|---|---|
| `pytest tests/ -v` | 跑整个 tests/ 目录 |
| `pytest tests/ -v -x` | 遇到第一个失败就停 |
| `pytest tests/ -v -k "alias"` | 只跑名字含 alias 的 |

### 为什么要测"反向"

- **正向**：该 True 的是 True（happy path）
- **反向**：该 False 的是 False（边界）

只测正向 → 抓不住"永远返回 True"的 bug（比如 `or True` 手滑）；只测反向 → 抓不住"永远返回 False"；**两个都测才完整**。

`test_blocked_contract` 遍历 11 条 SQL 是同一个哲学：**多方向覆盖，不靠"我觉得对"**。

## 二、test_guard.py 的 8 个用例

### 1. test_alias_column_hallucination

**防的坑**：§1.1 第 2 条——`sqlglot` 的 `col.table` 返回别名 `"o"`，不是真表名 `"orders"`。不建 alias 映射，`o.total_amount` 漏检。

```python
sql = "select o.total_amount from orders o"
assert v.passed is False
assert v.blocked is False
assert v.observation["kind"] == "UNKNOWN_COLUMN"
assert v.observation["source"] == "guard"
```

### 2. test_system_schema

**防的坑**：§2.11 的 `t.db` vs `t.name`。`mysql.user` 的 `t.name="user"`、`t.db="mysql"`。只比 `t.name` 会漏检系统表查询。

```python
sql = "select * from mysql.user"
assert v.blocked is True
assert v.observation["kind"] == "BLOCKED"
assert v.reason == "SYSTEM_SCHEMA_OR_CROSS_DB"
```

原理：`sql_guard.py` 读 `t.db`；`db in SYSTEM_SCHEMAS or db != "sqlpilot_demo"` → blocked。

### 3. test_unknown_table_hallucination

**防的坑**：§1.1 第 4 条——"系统库 → BLOCKED" vs "幻觉表名 → 可恢复" 的边界。

```python
sql = "select * from ordres"
assert v.blocked is False
assert v.observation["kind"] == "UNKNOWN_TABLE"
```

**分界**：表名前面**有 db 前缀** → 越权 → `BLOCKED`；**无 db 前缀** → 拼错 → `UNKNOWN_TABLE`（可恢复）。

### 4. test_cte

**防的坑**：CTE 临时名不是真表，不剔除会误判 `UNKNOWN_TABLE`。

```python
sql = "with temp as (select * from orders) select * from temp"
assert v.passed is True
assert v.normalized_sql.strip().upper().startswith("WITH")
assert "/*" not in v.normalized_sql
assert "--" not in v.normalized_sql
assert "#" not in v.normalized_sql
```

**CTE 剔除 vs alias 映射 —— 两个独立机制**：

- CTE 剔除 = "**减去不该查的**"（表名层面）
- alias 映射 = "**翻译成能查的**"（列前缀层面）

### 5. test_comment_bypass + test_comment_inside_string_ok

**防的坑**：SQL 里出现注释一律拦（注释是注入绕过手段）；但字符串里的 `--` 是数据，不该拦。

```python
# 拦截
sql = "select 1 --这是注释"
assert v.blocked is True
assert v.reason == "COMMENT_BYPASS"

# 放行
sql = "select * from orders where amount = '--299'"
assert v.passed is True
```

**原理**：注释是**代码结构**（有注入风险），字符串是**数据**（原样保留）。`_has_comment_outside_literals` 跟踪"是否在引号内"。

### 6. test_blocked_contract

**§2.11 契约**：任何 `blocked=True` 的分支，`observation["kind"]` 必须是 `"BLOCKED"`。

```python
for sql in blocked_sqls:
    assert v.blocked is True
    assert v.observation["kind"] == "BLOCKED"
```

覆盖 11 条 SQL：系统库 / 跨库 / 注释 / 多语句 / UNION / SLEEP / BENCHMARK / DROP / INSERT / UPDATE / @@version。

**防的是"行为对但证据错"**：

- 当前代码行为不会错（路由读 `blocked`，走 `refuse`）
- 但 Trace 里若 `kind="UNKNOWN_TABLE"`，**调试会被日志骗**——D11 badcase 归因会查错方向
- **契约的意义：行为正确 ≠ 证据正确**

### 7. test_unqualified_column

**§2.11 有意妥协**：裸列（无表别名）跳过检查，不误伤派生列/表达式列。

```python
sql = "select total_amount from orders"
assert v.passed is True           # 网关有意跳过
assert v.observation is None
```

**兜底链**：网关放行 → executor 打 DB → MySQL 报 `1054` → `ERRNO_KIND[1054] = "UNKNOWN_COLUMN"` → 进 loop 改写。

### 8. （可选）跨库 / UNION / 危险函数 / 零注释规范化

已被 `test_blocked_contract` 的 11 条 SQL 或 `test_cte` 的注释断言覆盖，不必单独写。

## 三、test_errors.py 的 3 个用例

### needs_relink 分派表（5 可恢复 kind）

| kind | needs_relink | 理由 |
|---|---|---|
| `UNKNOWN_COLUMN` | **True** | 注入真实候选列，需重检索 |
| `UNKNOWN_TABLE` | **True** | 注入候选表，需重检索 |
| `TYPE_MISMATCH` | **True** | 注入列类型和示例值（保守选重检索；若 D11 发现无收益可改 False） |
| `SYNTAX` | **False** | 语法错跟 schema 无关，重检索没用 |
| `OTHER` | **False** | 不认识的 errno，只做一次通用反思，省 token |

### is_recoverable / is_terminal 对称测试

- **正向**：5 个可恢复的 `is_recoverable` → True；4 个终止的 `is_terminal` → True
- **反向**：4 个终止的 `is_recoverable` → False；5 个可恢复的 `is_terminal` → False

## 四、关键概念

### 派生列 vs 表达式列

- **派生列**：`SELECT SUM(amount) AS total FROM orders`——`total` 原表不存在，是聚合算出的新名字
- **表达式列**：`SELECT amount * 1.1 FROM orders`——表达式本身就是一个"列"，但没名字

### 为什么"裸列"网关要跳过

```sql
SELECT total FROM (SELECT SUM(amount) AS total FROM orders) t
```

`total` 无表前缀 → 网关无法判断它属于哪张表（原表列 or 子查询派生列）。强行检查会**误杀合法 SQL**。

**选"跳过"**：

- 代价：真拼错（如 `total_amount`）要多一次 DB 往返
- 收益：不误伤派生列/表达式列
- 兜底：executor 的 `ERRNO_KIND[1054]` 接住

**这就是"有意的妥协"**——在"漏检（慢一点）"和"误杀（全挂）"之间选前者。

### 单元测试 vs 集成测试

| 类型 | 测什么 | 依赖 | 速度 | 挂了说明什么 |
|---|---|---|---|---|
| 单元测试 | 一个函数/类 | 无外部依赖 | 毫秒级 | 该函数写错 |
| 集成测试 | 多组件协作 | 真 MySQL / LLM | 秒级 | 组件连接处出问题 |
| 端到端 E2E | 整个系统 | 全套 | 分钟级 | 整条链路断了 |

**本项目分布**：

- `test_guard.py`（8 个）：**单元**，无依赖，0.2s
- `test_errors.py`（3 个）：**单元**，无依赖，0.04s
- `test_timeout.py`（3 个）：**集成 + 单元混合**，真 MySQL，3.5s

## 五、D5 超时测试 · 已知局限

### max_execution_time 的实际边界（实测发现）

| SQL 类型 | 是否生效 | 表现 |
|---|---|---|
| `SLEEP(N)` | ✅ **截断** | 3s 被 kill，**返回 0**（不抛 3024） |
| `BENCHMARK(N, expr)` | ❌ **不检查** | 跑完为止 |
| `COUNT(*) FROM a,b,c` | — | 优化器用行数相乘加速，瞬间返回 |
| 聚合查询 + `1ms` | ❌ **1ms 太小，不生效** | 一直跑到自然结束 |
| 聚合查询 + `3000ms` | 推测生效，未稳定验证 | 受机器性能影响 |

**关键发现**：`1ms` 超时值实际中无效（可能取整到 0 = 无限制）；`SLEEP` 被截断时不抛 3024。

### 最终测试方案（3 条）

```python
# 1. SLEEP 被 3s 截断（证明超时机制生效，用时 3.45s 而非 10s）
def test_query_timeout():
    t0 = time.monotonic()
    result = MySqlExecutor().execute("SELECT SLEEP(10)")
    assert time.monotonic() - t0 < 5      # 关键证据
    assert result["ok"] is True           # SLEEP 截断返回 0，不报错

# 2. errno 3024 的映射（纯数据，不用真连 DB）
def test_errno_3024_mapping():
    assert ERRNO_KIND[3024] == "QUERY_TIMEOUT"

# 3. QUERY_TIMEOUT 是终止类
def test_query_timeout_is_terminal():
    assert is_terminal("QUERY_TIMEOUT") is True
```

### 覆盖缺口（诚实记录）

| 项目 | 状态 |
|---|---|
| 真触发 `errno=3024` | ❌ **未覆盖**（SLEEP 截断返回 0，聚合查询不稳定） |
| SLEEP 被截断 | ✅ 已覆盖 |
| `ERRNO_KIND[3024]` 映射 | ✅ 已覆盖 |
| `QUERY_TIMEOUT` 是终止类 | ✅ 已覆盖 |

### 待改进

1. **`Settings.sql_timeout_s` 加下限**（≥ 0.1s）——防止误传 `0.001`，实际不生效
2. **D6 评测集里若需"超时"题**，用 `SLEEP` 而不是重聚合查询

### 面试可讲

> "写超时测试时发现 `max_execution_time` 对 `SLEEP` 和 `BENCHMARK` 这类函数等待不抛 3024——SLEEP 被截断返回 0。调整测试策略：用 `SLEEP + 耗时断言` 验证超时机制生效，用 `ERRNO_KIND` 单测验证 3024 的映射。这是**测试驱动的边界发现**，读文档得不到。"
