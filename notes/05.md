
pytest是什么
Python最常用的测试框架。
规则简单：文件名test_*.py,函数名test_*,运行时它
会自动发现并执行这些函数。执行顺序为pytest tests/test_guard.py -v

assert是什么
Python关键字，写法：
assert 条件，“失败时的提示”
条件为True——什么都不发生，测试继续
条件为False——抛AssertionError，pytest把这个测试标成红色FAILED
和if的区别：if是正常分支，assert是“我断定这里必须成立，不成立就是bug”。
测试文件里只用assert，不用if
is是什么：is比==严格————is判断是不是同一个对象，==判断值相等。测试里
断言True/False用is更准，因为True是单例。

常用组合（以后会用到）：
pytest tests/test_guard.py -v：详细
pytest tests/ -v：跑整个 tests/ 目录
pytest tests/ -v -x：遇到第一个失败就停（-x = exitfirst，调试时最有用）
pytest tests/ -v -k "alias"：只跑名字含 alias 的测试

-v 是什么意思
-v = verbose（详细模式）。对比：

不带 -v：
tests/test_guard.py .                                    [100%]
1 passed in 0.35s
一个 . 代表一个通过的测试，看不出测的是哪个。

带 -v（你刚跑的）：
tests/test_guard.py::test_alias_column_hallucination PASSED    [100%]
显示每个测试的完整名字 + 结果。

为什么要 -v：文件里有 10 个测试时，不带 -v 你只看到 ..........，哪个挂了要靠猜。带 -v 直接看到 test_xxx FAILED。

is vs ==（再强调一次，因为要用 4 次）
python
assert is_recoverable(k) is True     # 断言"返回值就是 True 这个对象"
assert is_recoverable(k) == True     # 断言"返回值等于 True"
对 bool 用 is：因为 True/False 是 Python 单例，is 判断"是不是同一个对象"最严格。如果函数返回 1（不是 True），is True 会挂，== True 不会——这正是我们想要的严格性。


派生列
select里通过计算造出来的列名，原表里不存在
eg:
select sum(amount) as total from orders
total不在orders表的列里，是聚合函数算出来的新名字。
eg:
select count(*) as cnt,AVG(price) as avg_price from products

表达式列
select里直接是表达式，没有别名
eg:
select amount * 1.1 from orders   --这个表达式就是一个“列”，但没名字
select sum(amount) from orders    --sum(amount)本身是表达式

为什么"裸列"网关要跳过
考虑这条 SQL：

sql
SELECT total FROM (SELECT SUM(amount) AS total FROM orders) t
total 是子查询的输出列。网关只解析最外层，它看到 total 没有表前缀（col.table 为空），无法判断 total 属于哪张表：

可能是 orders.total（假设 orders 有这个列）→ 存在 → 通过

也可能是子查询里的派生列 → 不存在于任何原表 → 网关误杀

网关没有能力区分这两种情况（要做完整的语义分析，成本太高）。所以选择跳过：让 MySQL 兜底，报 1054 就报 1054，反正 executor 会把 1054 转成 UNKNOWN_COLUMN 送进 loop。

代价：total_amount（真拼错）也要走"打 DB → 1054 → 改"的路径，比网关拦慢一点点（多一次 DB 往返）。
收益：不会误杀派生列/表达式列（否则合法 SQL 全挂）。

这就是"有意的妥协"——在"漏检（慢一点）"和"误杀（全挂）"之间选了前者。

## D5 关键理解

### is vs ==
- `==` 比较值，`is` 比较对象身份
- `1 == True` 是 True，`1 is True` 是 False
- 测 bool 用 `is`，因为能抓住"返回 1 而不是 True"的手滑
- 测其它类型用 `==`

### 为什么要测反向
- 正向：该 True 的是 True（happy path）
- 反向：该 False 的是 False（边界）
- 只测正向 → 抓不住"永远返回 True"的 bug（`or True` 手滑）
- 只测反向 → 抓不住"永远返回 False"的 bug
- 两个都测 → 两个方向都覆盖
- 和 `test_blocked_contract` 遍历 11 条 SQL 是同一个哲学：多方向覆盖，不靠"我觉得对"
