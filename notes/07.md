ensure_ascii 是什么（这是核心概念）
先讲 ASCII 是什么
ASCII = 美国信息交换标准代码，是最早、最简单的字符编码，只包含：

英文字母 a-z, A-Z

数字 0-9

常见符号 + - * / ( ) { } [ ] , . ; : ' " ? ! @ # $ % ^ & _ | ~ 等

控制字符（换行、制表等）

总共 128 个字符。

关键：中文不在 ASCII 里。上、海、门、店 都是"非 ASCII 字符"。

ensure_ascii 参数干什么
json.dumps() 把 Python 对象转成 JSON 字符串时，遇到中文有两种处理方式：

参数值	行为	输出
ensure_ascii=True（默认）	保证输出全是 ASCII	"\u4e0a\u6d77"
ensure_ascii=False	允许非 ASCII 字符	"上海"
为什么默认是 True
历史原因：JSON 规范 1999 年制定时，很多系统只支持 ASCII（早期 HTTP、邮件协议等）。为了"任何系统都能读"，默认把非 ASCII 字符转义成 \uXXXX。

\u4e0a 是什么：\u 后面 4 位十六进制是 Unicode 码点。4e0a = 上，6d77 = 海。这就是"汉字的本名"。

为什么这里要用 False
两个原因：

可读性：你的 v1.jsonl 是给人看的（D11 你会 grep 它、D13 面试官可能 cat 它）。"question": "\u4e0a\u6d77" 你看不出是"上海"，"question": "上海" 一眼就懂。

文件大小：上海 是 2 个汉字（UTF-8 占 6 字节），\u4e0a\u6d77 是 12 个 ASCII 字符（12 字节）。转义后体积翻倍。

核心记忆：

ensure_ascii=True = "输出全 ASCII，中文变 \uXXXX"
ensure_ascii=False = "输出保留 UTF-8，中文正常显示"

比如 16 道题，中文总共几千字。True 时每汉字变 6 字节 ASCII，False 时每汉字 3 字节 UTF-8——False 大约小 50%。

这就是"为什么开源项目里 JSON 文件都用 ensure_ascii=False"——不只是好看，是真的省空间。

二、getattr(mod, "c") 是什么
先讲 Python 里"取属性"的两种写法
python
# 写法 A：点号（最常用）
value = mod.c

# 写法 B：getattr（用字符串名字取）
value = getattr(mod, "c")
两种写法效果完全一样——都是"从 mod 这个对象里，取出名为 c 的属性"。

那为什么要用 getattr 而不直接 mod.c
因为 mod 是动态的。看 tmp_dump.py 的循环：

python
for f in sorted(seeds_dir.glob("E*.py")):
    mod = importlib.import_module(f"sqlpilot.eval._seeds.{f.stem}")
    c = getattr(mod, "c", None)   # ← 每个循环 mod 都是不同的模块
第 1 轮：mod 是 E01.py 模块

第 2 轮：mod 是 E02.py 模块

...

每个模块里都有 c 变量（EvalCase 对象），所以 mod.c 也能取到。getattr 在这不是"必须的"，只是"更稳"。

getattr 真正的价值：第三个参数
python
c = getattr(mod, "c", None)
#                     ^^^^ 默认值
意思是：如果模块里没有 c 这个属性，不要报错，返回 None。

对比：

python
c = mod.c              # 如果 mod 里没有 c，直接抛 AttributeError → 整个循环崩
c = getattr(mod, "c", None)   # 没有 c 时返回 None → 可以继续处理下一题
这就解释了为什么 E01 漏了 c 时 tmp_dump 没崩——它用 getattr(..., None) 拿到 None，走 if c is None: print("⚠️ 没有 c 变量"); continue 分支，跳过 E01 继续处理 E02。如果没有默认值 None，mod.c 会直接抛异常，整个 dump 就死了。

一句话：getattr(obj, "name", default) = "取 obj.name，没有就返回 default（不报错）"。

if __name__ == "__main__": 为什么能阻止导入时执行
先讲 __name__ 是什么
每个 .py 文件都有一个内置变量 __name__。它的值取决于"这个文件怎么被使用"：

使用方式	__name__ 的值
直接运行 python E01.py	"__main__"
被导入 import E01 或 importlib.import_module("E01")	"E01"（模块名）
这是 Python 的约定——Python 解释器判断"当前文件是主程序还是被导入的库"，就靠看 __name__ 的值。

用一个最小例子看
demo.py：

python
print("文件被加载了，__name__ =", __name__)

if __name__ == "__main__":
    print("这是主程序入口")
场景 1：直接运行

powershell
python demo.py
输出：

text
文件被加载了，__name__ = __main__
这是主程序入口
场景 2：被导入

powershell
python -c "import demo"
输出：

text
文件被加载了，__name__ = demo
注意："这是主程序入口" 没打印！

为什么这样设计
核心事实：Python 导入一个模块时，会执行该模块顶层的所有代码（函数定义、变量赋值、print 都会执行）。

问题：E01.py 的顶层有 r = MySqlExecutor().execute(...) 和 print(...)——tmp_dump.py 导入 E01 时，这段验证代码自动跑一遍，会连数据库、打印结果。

这带来两个后果：

慢：dump 一次要连 16 次数据库（每道题都跑一次 GT SQL）

吵：输出里混了一堆 rows: 4 之类的验证日志（你刚才贴的输出就有）

if __name__ == "__main__": 的作用：

直接运行 E01.py（python E01.py）：__name__ == "__main__" → 进入 if 块 → 执行验证

被 tmp_dump 导入：__name__ == "sqlpilot.eval._seeds.E01" ≠ "__main__" → 不进 if 块 → 不执行验证

一句话：if __name__ == "__main__": 是"这段代码只在直接运行本文件时执行，被其他文件导入时不执行"的标准写法。

print(f"{v!r:30s} ...") 逐段解释
python
print(f"{v!r:30s} tol={tol}  →  {normalize_value(v, tol)!r}")
拆成 3 个 {} 看：

片段	含义	输出

{tol}	直接插入 tol 的值	0.01

!r 是什么：repr() 和 str() 的区别——

python
>>> s = "abc"
>>> print(str(s))     # abc        （给人看）
>>> print(repr(s))    # 'abc'      （给解释器看，带引号）

>>> from decimal import Decimal
>>> print(str(Decimal('18348.85')))   # 18348.85
>>> print(repr(Decimal('18348.85')))  # Decimal('18348.85')
为什么要 !r：调试输出时用 repr 能看出类型（Decimal vs float）和精确值（不带格式化的截断）。str 会美化，repr 不会
"带容差的 float 不可哈希"到底是什么意思
先说：float 本身可以哈希
python
>>> hash(1283400.5)
1934863653548781683
>>> hash(1283400.5000000002)
1934863653548781689   # 不同的哈希值！
float 有 __hash__，能用。问题不在"不能哈希"，在"容差内的两个 float 哈希不同"。

为什么这会让 Counter 失效
Counter（多重集）用 __eq__ + __hash__ 判断元素是否相同：

python
from collections import Counter

a = 1283400.5000000002
b = 1283400.50

Counter([a, b])   # 结果：{1283400.5000000002: 1, 1283400.5: 1}
                  # 它认为这是两个不同的值！
因为 a != b 且 hash(a) != hash(b)——Counter 眼里它们是两个独立元素。

但你语义上认为它们"相等"（容差范围内）。Counter 不理解"容差"这个概念——它只认"== 和 hash 完全一致"。

所以"必须先量化"
量化的目标：把"容差内"的所有值，映射到同一个 bit 模式的 float。

python
a_q = normalize_value(a, 0.01)   # → 1283400.5
b_q = normalize_value(b, 0.01)   # → 1283400.5
Counter([a_q, b_q])   # → {1283400.5: 2}
现在 Counter 认为它们是同一个值，计数是 2——正确。

一句话总结
"带容差的 float 不可哈希" 不是"float 不能哈希"，而是 "容差内的两个 float 哈希不同，Counter 会把它们当成两个元素"。所以必须先量化到"同一 bit 模式"，才能用 Counter。

hash() 是什么
hash(x) 把任意对象变成一个整数（叫"哈希值"）。

python
>>> hash("abc")
-1921318913450563789
>>> hash(42)
42
>>> hash(1283400.5)
1934863653548781683
用途：快速判断"两个对象是不是同一个"。哈希值不同的对象，一定不同；哈希值相同的，可能相同（还要再比 ==）。

为什么需要它：如果 100 万个元素两两比较 ==，要 5000 亿次；如果先比 hash，哈希不同的直接跳过，瞬间筛掉 99.99%。

 "同一个 key" 是什么
Counter 内部是一个 dict：

python
Counter(['a', 'a', 'b'])   # 结果：Counter({'a': 2, 'b': 1})
它内部存的是：

python
{'a': 2, 'b': 1}
#  ^       ^
#  key    value（计数）
"key" 就是 dict 的键——在 Counter 里是"元素本身"。

Counter 判断两个元素"是不是同一个 key" 靠两步：

hash(元素) 是否相等

如果 hash 相等，再 元素1 == 元素2

所以"同一个 key" = "hash 相等且 == 为 True"。

回到你的场景：

python
a = 1283400.5000000002
b = 1283400.50
hash(a) == hash(b)?   # False（两个不同的哈希值）
a == b?               # False
# → Counter 把它们当成两个不同的 key，计数各为 1
量化后：

python
a_q = 1283400.5   # 和 b_q 完全相同
b_q = 1283400.5
hash(a_q) == hash(b_q)?  # True
a_q == b_q?              # True
# → Counter 把两个当成同一个 key，计数为 2
这就是"让容差内的值变成同一个 key"的意思——不是"变成同一个变量"，是"在 Counter 内部被当成同一个 dict 键"

bit 模式"是什么——不是小数点位数相同
这是最容易误解的地方。float 在内存里是 64 个二进制位（0/1），按 IEEE 754 标准拆成：

部分	位数	作用
符号位	1	正/负
指数位	11	数量级（10 的多少次方）
尾数位	52	具体数值
两个 float "bit 模式相同" = 这 64 位完全一样。

用代码直接看 bit 模式
python
import struct

def bits(f):
    return struct.pack('>d', f).hex()   # 把 float 的 8 个字节转成十六进制

a = 1283400.5000000002
b = 1283400.50
print(bits(a))   # 4133961690000000
print(bits(b))   # 4133961690000000   ← 完全相同！
print(a == b)    # 但 a == b 是 False！
等等，上面这个例子 a == b 是 False 但 bits 相同？

这是 Python 的一个特殊之处：== 会做"近似比较"，但 hash 和内部存储是 bit 级的。实际上：

python
>>> a = 1283400.5000000002
>>> b = 1283400.50
>>> a == b
False                    # 严格比较，不等
>>> struct.pack('>d', a).hex() == struct.pack('>d', b).hex()
True                     # 但 bit 模式相同！

# 为什么？
>>> a
1283400.5                # 打印出来是 1283400.5！
>>> b
1283400.5
真相：1283400.5000000002 在赋值给 Python float 时，因为双精度只有 15-17 位有效数字，.5000000002 这 10 位小数被截断了——它和 1283400.50 在内存里根本就是同一个 float。

所以你的验证：

python
a = normalize_value(Decimal('1283400.5000000002'), 0.01)   # → 1283400.5
b = normalize_value(1283400.50, 0.01)                      # → 1283400.5
a == b  # True
这个 True 不是量化"造"出来的，是 float 精度本来就只有 15-17 位——.5000000002 存不进去。

那量化的真正作用是什么？

量化的真正作用（对小数位更多的值）
考虑一个真正有更多小数位的值：

python
a = 18348.850000000002     # 小数点后 12 位
b = 18348.85               # 小数点后 2 位
python
>>> bits(a)   # 40d1e8d9999999999a
>>> bits(b)   # 40d1e8d9999999999a
>>> a == b
True                       # 在 float 精度内，其实相等
这是 18348.85 的 float 表示——18348.85 转 float 时，0.85 在二进制里无法精确表示，最终存成一个"最接近 .85 的 64 位值"。两个"不同来源"的 .85 恰好落在同一个 64 位值上，所以 == 是 True。

量化的作用在更极端的情况：

python
a = 18348.853       # 多出 0.003
b = 18348.85        # 原值
python
>>> a == b
False                   # 0.003 > 容差，确实不等
>>> normalize_value(a, 0.01)   # → 18348.85
>>> normalize_value(b, 0.01)   # → 18348.85
>>> a == b  # 量化后
True                    # 量化把 0.003 的差异"抹平"到 .01 精度
这才是量化的核心价值：

量化 = "按容差精度四舍五入"。容差 0.01 意味着"精确到分"，18348.853 和 18348.85 在"分"精度上都是 18348.85，所以判等。

一句话总结三个概念
概念	一句话
hash()	把对象变成整数，用于快速判断"是不是同一个"
同一个 key	Counter 内部 dict 的键，靠 hash 相等 + == 判断
bit 模式	64 个二进制位完全一致；不是小数点位数相同，是内存里存储完全相同
量化	按容差精度四舍五入，把"容差内"的值拉成同一个 bit 模式

map 是什么：map(func, iterable) 对 iterable 里每个元素应用 func。map(tuple, [[1, 100], [2, 200]]) → [(1, 100), (2, 200)]。

为什么必须转 tuple：list 不可哈希（hash([1]) 报 TypeError: unhashable type: 'list'），tuple 可哈希。Counter 要求元素可哈希，所以 [1, 100] 不能直接进 Counter，要转 (1, 100)。

整个 compare.py 到底要干什么（重新解释一遍）
一句话
判断"模型 SQL 的执行结果"和"标准答案的执行结果"，是不是"同一个答案"。

为什么这么复杂，不能直接 pred == gt
因为有 4 个坑（对应 4 个函数/步骤）：

坑	例子	怎么处理
坑 1：浮点精度	18348.85 存 float 后是 18348.850000000002，== 失败	normalize_value 量化到 tolerance 精度
坑 2：Decimal vs float	GT 返回 Decimal('18348.85')，模型返回 float 18348.85，== 失败	normalize_value 统一转 float
坑 3：列序不同	SELECT a, b 和 SELECT b, a 语义相同，但 == 逐位置比失败	_align_columns 按列名重排
坑 4：行序不同	GT SQL 无 ORDER BY 时，MySQL 返回顺序随机	检测 GT SQL 有无 ORDER BY，无则用 Counter 忽略顺序
完整流程（这就是 compare() 的职责）
text
输入：pred_result（模型结果）、gt_result（标准答案）、gt_sql
  ↓
[1] 行数不同？ → 直接判错（长度都不一样，内容怎么相同）
  ↓
[2] 列对齐：_align_columns（按列名重排 pred，对齐 gt）
  ↓
[3] 每单元格：normalize_value（Decimal→float，浮点量化）
  ↓
[4] 检测 gt_sql 有无 ORDER BY
  ↓
[5a] 有 ORDER BY → pred_norm == gt_norm（按行序逐行比）
[5b] 无 ORDER BY → Counter(pred_norm) == Counter(gt_norm)（忽略行序）
  ↓
输出：(passed: bool, reason: str)
为什么返回 (passed, reason) 而不是只返回 bool
reason 是给 D11 badcase 归因用的。举个例子：

row_count_mismatch: 3 vs 5 → 模型返回 3 行，GT 5 行 → 可能模型漏了 GROUP BY

column_misalignment → 列名集合不同 → 可能模型选了错误的列

ordered_mismatch → 保序题顺序错了 → 可能模型忘了 ORDER BY 或排序字段错

content_mismatch → 行数相同但内容不同 → 可能模型过滤条件错（比如忘了 LOWER(TRIM())）

reason 让 D11 一眼知道"错在哪类"，不用重新跑模型。

1	ORDER BY 保序 + 完全一致	有 ORDER BY，行序一致	(True, 'ordered_compare_ok')	分支 5a，逐行比全等
2	ORDER BY 保序 + 行序错	有 ORDER BY，行序颠倒	(False, 'ordered_mismatch')	分支 5a，逐行比失败
3	无 ORDER BY + 行序不同	无 ORDER BY，行序颠倒	(True, 'multiset_compare_ok')	分支 5b，Counter 认为相同
4	无 ORDER BY + 列序不同	pred 列序 ["b","a"]，gt 列序 ["a","b"]	(True, 'multiset_compare_ok')	_align_columns 重排 → 分支 5b
5	浮点容差	18348.853 vs 18348.85，tol=0.01	(True, 'multiset_compare_ok')	normalize_value 量化 → 分支 5b
测试 1 vs 测试 2：同样的 SQL，只是行序不同 → 一个 True 一个 False。这证明"ORDER BY 时保序"是对的。

测试 2 vs 测试 3：同样的结果集（行序颠倒），只是 GT SQL 有无 ORDER BY → 一个 False 一个 True。这证明"无 ORDER BY 时忽略顺序"是对的。

这 5 条测试就是 §4.4 两个陷阱的验证：

陷阱 1（浮点）：测试 5

陷阱 2（列序/行序）：测试 2、3、4

为什么要分两个文件
单一职责：

compare.py 只做"判等"这一件事，能独立单测（你刚写了 2 条测试）

runner.py 只做"调度"这一件事，调用的东西全部外部传入（agent、executor、compare）

好处：

如果 D11 发现判等逻辑有 bug，只改 compare.py，不动 runner.py

如果 D11 发现 runner 的统计逻辑错，只改 runner.py，不动 compare.py

两个文件可以分开测（compare.py 用 mock 数据测，runner.py 用真 DB 测）

python -m sqlpilot.eval 这个命令，Python 会去找 sqlpilot/eval/__main__.py 这个文件——它是"包被当作命令直接执行时"的入口。

你写的是 runner.py，但 Python 不知道去调它。这是 Python 的 -m 机制：python -m 包名 = 执行 包名/__main__.py。

对比：

powershell
python -m sqlpilot.eval.runner validate    # ✅ 能跑（直接指定模块）
python -m sqlpilot.eval validate           # ❌ 需要 __main__.py
文档 §4.7 用的是后者（python -m sqlpilot.eval validate），所以必须补 __main__.py。

逐行解释：

行	作用
from sqlpilot.eval.runner import main	从 runner.py 导入 main 函数
sys.exit(main())	调 main()，把返回码传给系统（0=成功，1=失败）
为什么 sys.exit(main()) 而不是直接 main()：

main() 返回 int（0 或 1）

直接 main() 不传返回码给系统，shell 看到的永远是 0

sys.exit(0) = 正常退出；sys.exit(1) = 错误退出

CI 里靠这个返回码判断"评测集 validate 过没过"（$LASTEXITCODE）

cmd_run 干什么（数据流 5 步）
Step 1: 强制 --split dev/heldout（D7 DoD 要求）→ 没带就报错
Step 2: 从 v1.jsonl 读题，只保留 split == args.split 的
Step 3: 逐题跑：
  3a. 调 graph.run(question) → 拿 agent_out（含 sql, final_status, failure_reason）
  3b. 按 expect 分支判对错
  3c. 记录 {id, passed, reason}
Step 4: 统计 passed / total
Step 5: 打印汇总

D6 做对比实验时改了 GT SQL 忘了改回来——这是评测集冻结机制存在的理由（§4.3 Step 4 "冻结 + sha256"）。

D7 的 cmd_validate 本该抓到这个问题——但它只检查"GT SQL 能不能执行"，不检查"GT SQL 是不是对的"。

更严格的 validate 应该检查：

GT SQL 的结果集，和"人工标注的预期结果"是否一致

但 D6 没做"预期结果标注"——这就是"评测集质量"的深层问题：GT SQL 能跑 ≠ GT SQL 是对的。

D11 如果发现某道题的 GT 有问题，要记录并修，这是真实的评测工程。面试时能讲："我在 D7 发现 E03 的 GT SQL 是 D6 对比实验遗留的错误版本，这让我加了验证流程——每次改 GT 必须重新跑 validate 确认结果符合预期。"
