## 今日重大发现（两个，都是真问题，不是瞎猜）

### 发现1：修复了一个严重 bug —— LLM 计数器跨题污染
- 现象：单跑 S07 retry=2、批量跑 retry=0；批量里从第 N 题起 retry 恒为 0。
- 根因：LLMClient.llm_calls 是累加器，runner 复用同一个 LLMClient 跑多题时不清零，前面题把 max_llm_calls(=6) 预算吃光 → 后面题 _budget_ok 一进来就 False → 直接 MAX_RETRY_EXCEEDED，attempts=1 放弃。
- 证据：单跑 llm_calls 从 0 起够用；批量跑到 S07 时 llm_calls 已累计 9>6。
- 修复：graph.py 的 QueryGraph.run 开头重置 llm 的 prompt_tokens/completion_tokens/llm_calls（commit 8d7af9b）。
- 影响：修复前所有批量数据（含 dev G0/G1/G2）都受污染；修复后压力集触发率从 3.3% → 36.7%，出现真实"纠错救回"案例。
- 教训：复用有状态对象跑批量，必须每轮重置其累加器。

### 发现2：压力集触发率低 ≠ 模型太强那么简单
经三层机制分析（Zcode 审计 + 实测印证）：
- 机制一：24 张占位表"有列但空表"（members.points/payments.method/inventory.safety_stock 都存在且 0 行）→ 查空集 success、不报错 → 不触发。
- 机制二：题面无 synonyms 业务词（供应商/仓库/库存）→ retriever 返回 [] → 直接 refuse，不走纠错。
- 机制三：部分 tagged 列其实存在（orders.amount/qty 等）→ 一次写对。
- 结论：不触发分两类——安全拒答（B类，能力）和空表成功（C/D类）；不能都把锅甩给"模型强"。

### 发现3：LLM 评测本身有抖动（temperature=0 也不保证复现）
- G2 连跑两次：14/16、15/16，差异在 E16。
- 逐题对比定位：E16 两次生成近等价但写法不同的 SQL（tie-breaker、条件位置），碰上并列值排序 → ordered_mismatch 翻转。
- 结论：端到端波动 = 模型生成抖动 + 比较器对 ORDER BY/列对齐敏感，不是单纯服务端随机采样。
- 应对：跑 10 次取区间 + 逐题稳定性，而非单次下结论。

## 今日核心概念
1. 消融实验：G2 vs G0 看检索价值、G2 vs G1 看纠错价值，一次只变一个变量。
2. G0 全量表 = FakeFullRetriever 注入（依赖注入，不改 retriever.py）；G1 无纠错 = model_copy(max_retries=0)（独立副本，不污染单例）。
3. 错两类：执行错误（DB报错，可被纠错抓）vs 静默语义错（跑通但业务不对，纠错抓不到）。
4. E05 = 稳定错（能力缺陷）；E16 = 抖动错（生成/排序敏感）。
