## 今日核心概念
1. 镜像(只读模板) vs 容器(运行实例) vs 仓库(Registry)。
2. Dockerfile(造一个镜像) vs docker-compose.yml(编排多容器)。
3. Dockerfile 关键行：FROM(python:3.11-slim) / WORKDIR / COPY requirements→pip install→COPY . .(分层缓存：变慢的放前) / CMD(默认启动，可被 compose command 覆盖) / --host 0.0.0.0(容器内必须听全网卡)。
4. Docker 分层缓存：只重建变更层，pip 依赖层未变则复用缓存。
5. 配置与代码分离：config.py 用 pydantic-settings 读环境变量(字段名大写=env名)，优先级 进程环境变量 > .env > 默认值。compose environment/env_file 注入的是第一优先级，容器里无需 .env。
6. 容器网络：服务名=主机名。app 连 mysql 用 MYSQL_HOST=mysql:3306；web 连 app 用 http://app:8000。
7. 端口映射 ports "A:B"：A=宿主机，B=容器内。mysql 3307:3306（宿主3307避免与本机3306冲突）。
8. depends_on + condition：service_healthy(等健康检查通过) / service_completed_successfully(等一次性任务成功退出)。app 必须等 seed 灌完数据。
9. healthcheck：用真实 SELECT 验证 readiness（就绪），不是 liveness（进程活着）。
10. seed 一次性容器：灌完数据 exit 0，restart:"no"；有幂等保护(seed.py:208)。down -v 可清数据重灌。
11. 一个镜像两个容器：app 用默认 CMD(uvicorn)，web 用 compose command 覆盖(streamlit)。互不影响。
12. CI = push/PR 时在干净云端机器自动跑 lint+test+validate；防坏代码合入主分支。

## 2. 完整流程

### 阶段一：连接服务器 + 安装 Docker

```bash
# 本地 PowerShell 连接
ssh lighthouse
```

安装 Docker 时踩了第一个坑：

```bash
# ❌ 失败：Ubuntu 官方源里没有 docker-compose-plugin
sudo apt install -y docker.io docker-compose-plugin
# E: 无法定位软件包 docker-compose-plugin
```

原因：`docker-compose-plugin` 只在 Docker 官方源里有，Ubuntu 自带源没有。

诊断命令（只读，查有哪些包可用）：

```bash
apt-cache search docker | grep -i compose
```

发现 `docker-compose-v2`（Ubuntu 24.04 的替代包），改用：

```bash
# ✅ 成功
sudo apt install -y docker.io docker-compose-v2
sudo systemctl enable --now docker
sudo usermod -aG docker $USER
```

`usermod` 加组后必须**退出 SSH 重新连**才生效：

```bash
exit
ssh lighthouse
```

验证：

```bash
docker ps                    # 不报错即用户组生效
docker compose version       # ✅ 可用（空格形式）
docker-compose version       # ❌ 不存在（横杠形式）
```

> 知识点：Ubuntu 24.04 的 docker-compose-v2 提供的是 `docker compose`（空格，CLI 插件），
> 不是 `docker-compose`（横杠，独立二进制）。后续所有命令都用空格形式。

### 阶段二：打包上传（配置分离）

**核心决策：配置和代码分离。** `.env`（含真实密钥）不进包，到服务器单独生成。

本地打包（在 `D:\PythonProject` 目录下，用 tar 排除敏感文件）：

```powershell
cd D:\PythonProject
tar --exclude='Sqlpilot/.env' --exclude='Sqlpilot/.git' --exclude='Sqlpilot/.idea' `
    --exclude='Sqlpilot/.pytest_cache' --exclude='Sqlpilot/.ruff_cache' `
    --exclude='Sqlpilot/data/traces' --exclude='*/__pycache__' `
    -czf sqlpilot-full.tar.gz Sqlpilot
scp sqlpilot-full.tar.gz lighthouse:/home/ubuntu/
```

服务器上解包并生成 `.env`：

```bash
cd /home/ubuntu
tar -xzf sqlpilot-full.tar.gz
cd /home/ubuntu/Sqlpilot
cp .env.example .env
nano .env          # 填入真实值
chmod 600 .env     # 只有属主可读
```

验证关键变量都在（只显示变量名，不显示值）：

```bash
grep -oE '^[A-Z_]+=' .env | sort
```

> 为什么配置分离：
> 1. `.gitignore` / `.dockerignore` 只管 Git 和镜像，scp 不看它们，整目录传会把 .env 带上去
> 2. 项目架构本来就是这么设计的（compose 用 ${VAR} 插值，Dockerfile 里 .dockerignore 挡住 .env）
> 3. 将来传 GitHub、换服务器、key 泄露排查，配置分离都能省事

### 阶段三：启动 Docker 服务

### 阶段五：Caddy 反向代理 + Basic Auth（解决家里 IP 变化问题）

**问题**：防火墙白名单写家里 IP，但家宽 IP 会变，一变全家都连不上。

**思路**：不认 IP，认密码。谁都能连端口，但要输密码才能用。

先只读检查服务器 Caddy 结构：

```bash
cat /etc/caddy/Caddyfile
ls -la /etc/caddy/acli.d/sites/
```

发现：
- Caddy v2.11.7，支持 basic_auth
- Caddyfile 最后 `import "/etc/caddy/acli.d/sites/*.caddy"`
- 所以只要往 sites 目录加一个新文件，就会被自动加载，不碰 Hermes 原有的配置

生成密码哈希（交互式，密码不进历史）：

```bash
caddy hash-password
# 输入两次密码，得到 $2a$14$... 开头的哈希
```

新建站点配置：

```bash
sudo tee /etc/caddy/acli.d/sites/sqlpilot.caddy <<'EOF'
:8502 {
        basic_auth {
                family <这里粘贴密码哈希>
        }
        reverse_proxy 127.0.0.1:8501 {
                header_up Host 127.0.0.1:8501
        }
}
EOF
```

验证语法：

```bash
sudo caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile
# Valid configuration
```

重载（踩坑）：

```bash
# ❌ 失败
sudo systemctl reload caddy
# Post "http://localhost:2019/load": connection refused
```

原因：Caddyfile 里有 `admin off`，管理端口 2019 关闭，reload 无法把配置递给运行中的实例。

```bash
# ✅ 成功：用 restart，不走管理端口
sudo systemctl restart caddy
```

验证：

```bash
ss -tlnp | grep 8502
curl -s -o /dev/null -w "无密码: %{http_code}\n" http://127.0.0.1:8502   # 401
curl -s -o /dev/null -w "有密码: %{http_code}\n" -u family:<密码> http://127.0.0.1:8502   # 200
```

最后在腾讯云控制台放行 TCP 8502，来源 0.0.0.0/0。

家人访问：`http://82.157.107.233:8502` → 输密码 → 可用。IP 再怎么变都不影响。

## 4. 核心概念理解

### 配置分离
密钥不进代码、不进镜像、不进版本库。运行时通过环境变量注入。
`.gitignore` 管 Git，`.dockerignore` 管镜像，**scp 两个都不看**——这是最容易踩的点。

### SSH 隧道
把服务器的端口"借"到本地。设备级访问，最安全，不暴露公网端口。
缺点：那个 PowerShell 窗口关了就断。

### 反向代理 + Basic Auth
Caddy 在前面挡一道密码，后面转给 Streamlit。
好处：不认 IP 认密码，解决动态 IP 问题，同时提供公网访问的安全屏障。

### Docker Compose
一个文件编排多个容器（数据库 + 灌数 + 后端 + 前端），一条命令全部启动。

---

### Web 访问的本质：从这次部署看懂通用原理

> 这一节是今晚实践背后的理论框架。理解了它，以后部署任何 Web 应用都是这套逻辑的排列组合。

#### 1. 一个网页是怎么被访问到的

```
你的浏览器 ──网络──▶ 服务器公网IP ──防火墙放行──▶ 端口 ──▶ 端口上跑着的Web服务 ──▶ 返回网页
```

"能从浏览器访问" = 三件事同时成立：

| # | 条件 | 这次是怎么满足的 |
|---|---|---|
| 1 | 服务器上跑着 Web 服务（能吐出网页的程序） | Streamlit 在 8501 跑着 |
| 2 | 服务器有公网 IP | `82.157.107.233` |
| 3 | 网络通路打通（防火墙/端口/反向代理） | 防火墙放行 8502 + Caddy 反代 + 密码门 |

> 服务器只是"一台永远开着的电脑"。没跑 Web 程序之前它就是空壳——SSH 能连，浏览器打开 IP 什么都没有。
> 比喻：服务器 = 地皮+房子，Web 服务 = 店里卖网页，公网 IP = 门牌号，防火墙 = 开门，Caddy+密码 = 门口保安。

#### 2. 公网 IP 是什么

公网 IP = 互联网上的"电话号码"，全球唯一，别人靠它找到你的服务器。
内网 IP（私有 IP）= 内部"分机号"，如 `192.168.1.5`、`10.2.0.13`，外面看不到，不同网络可以重复。

| | 公网 IP | 内网 IP |
|---|---|---|
| 类比 | 对外公开的电话号码 | 公司内部的分机号 |
| 谁能访问 | 全互联网任何人 | 同一局域网内设备 |
| 会不会重复 | 全球唯一 | 不同网络可重复 |

为什么家里没有公网 IP：IPv4 地址不够用（全球约 43 亿个，早分光了），运营商用 NAT 让千家万户共享少量公网 IP——一栋楼一个总机号码，各户是分机，外面打进来需要转接。
云服务器为什么有：花钱租用，腾讯云分配专属公网 IP。

#### 3. 内网穿透：让没有公网 IP 的设备也能被访问

NAT 让外部无法直接找到家里设备，内网穿透技术绕开这个限制。

| 工具 | 原理 | 难度 | 花钱吗 |
|---|---|---|---|
| Tailscale | 组私密虚拟局域网（VPN），设备间互相可见 | ⭐ 装客户端登录即可 | 免费版够个人用 |
| 花生壳 | 第三方中转，给免费域名指向你家 | ⭐ 简单 | 免费版有限制，好用的付费 |
| frp | 自建中转：需一台有公网 IP 的服务器做跳板 | ⭐⭐ 配服务端+客户端 | 软件免费，但要有那台服务器 |

**重点**：frp 需要的"有公网 IP 的服务器"你已经有了（就是这台云服务器），所以可以零额外成本实现：

```
云服务器跑 frp 服务端 → 家里电脑/NAS 跑 frp 客户端连上去
→ 外部访问云服务器某端口 → 被转发到家里设备
```

难度不大——和今晚做的端口转发、反向代理是同一类思路，照教程半小时能通。

#### 4. 域名与备案

- **域名**：给 IP 起的好记名字（如 `baidu.com`），一年几十块
- **DNS**：互联网的电话簿，把域名翻译成 IP
- **解析**：在 DNS 里设置"这个域名指向这个 IP"
- **备案**：中国大陆法规，用域名 + 80/443 对外提供网站服务必须实名登记（ICP 备案）。免费、腾讯云可代办，但要提交身份证、拍照核验、审核 10~20 天

**你的情况不需要备案**：用的是 IP + 高位端口（8502），没用域名也没用 80/443。
**什么时候需要**：想让别人用 `https://你的名字.com` 这样好看又安全的地址访问时。

#### 5. 不是所有 Web 都是"放行端口 + 用户名密码"

那只是比较简陋的一种。真实 Web 分三层：

```
第1层 网络层：端口（80/443 是默认，地址栏不显示）
第2层 传输层：HTTP（明文）vs HTTPS（加密，需 SSL 证书）
第3层 应用层：认证方式（用什么证明"你是谁"）
```

应用层认证方式五花八门：

| 方式 | 长什么样 | 谁在用 |
|---|---|---|
| Basic Auth 弹窗 | 浏览器弹框输用户名密码 | 本次项目（Caddy 加的，最简单） |
| 表单登录 + Session/Cookie | 网页登录框，登录后保持状态 | 绝大多数网站：知乎、淘宝、GitHub |
| 第三方登录 OAuth | "用微信/Google/GitHub 登录" | 各种 App 和网站 |
| API Key / Token | 请求头带一串密钥 | 程序间调用（你的 LLM 调用就是） |
| SSH 密钥 | 私钥文件证明身份 | 你连服务器的 `ssh lighthouse` |
| mTLS 双向证书 | 双方出示证书 | 银行、企业内部 |

为什么你的项目是 Basic Auth：Streamlit 本身没有登录功能（设计给内部工具用），所以在 Caddy 反向代理层加了密码门。这是常见技巧——**给没有登录功能的服务，在反向代理层加一道认证**。

成熟网站（以知乎为例）的链路：

```
浏览器 → https://www.zhihu.com（443 + HTTPS + 域名 + 备案）
   → CDN（就近加速、隐藏真实 IP）→ 负载均衡 → 应用服务器
   → 输入手机号/密码 → 验证 → 发 Cookie
   → 之后每次请求带 Cookie，就知道是你了
```

区别：域名+HTTPS（好看、加密、要备案）、应用层登录（不弹窗、体验好、能管权限）、CDN+负载均衡（扛大流量、隐藏真实 IP）。

#### 6. 一张图总结

```
公网 IP    = 电话号码（云服务器有，家里没有）
域名      = 给号码起的名字（要买，大陆用要备案）
备案      = 大陆网站实名登记（用 IP+高位端口暂时不需要）
内网穿透  = 让没公网 IP 的家里设备借云服务器的号码被访问（frp/Tailscale/花生壳）
端口      = 房子开哪扇门
认证      = 门口怎么验身份（你：Basic Auth 弹窗；大网站：登录框+Cookie）
HTTPS     = 给通信加密（现在没有，将来上域名时可加）
```

> 核心结论：有公网可达的服务器是基础，但要跑 Web 服务、开端口/配反向代理、加认证，浏览器才能访问。认证方式五花八门，但底层逻辑和今晚做的一样——让一个程序在网络上被安全地访问。

## 6. 安全事项

1. **密码不要写进笔记/代码/聊天记录**
2. 密码要复杂：字母+数字+符号，12 位以上
3. `.env` 权限设为 600
4. 8501 端口始终不对外放行，只放行带密码的 8502
5. LLM API Key 会烧 token，建议在服务商后台设每日额度上限
