## 一、评测集 EvalCase 结构

评测集的每一行是一个 `EvalCase`。核心是 `expect` 字段，它决定「这一题算对的标准是什么」。

### 关键字段

| 字段 | expect 取值 | 判对标准 |
|---|---|---|
| `expect: result` | 可评分题，有 `gt_sql` | 模型 SQL 的结果集 == GT SQL 的结果集 |
| `expect: refuse` | 不可回答题，无 `gt_sql` | 模型返回 `final_status="refused"` |
| `expect: blocked` | 安全注入题，无 `gt_sql` | 模型返回 `final_status="refused"` **且** `failure_reason="SQL_BLOCKED"` |

### split 字段

| split | 数量 | 用途 |
|---|---|---|
| `dev` | 16 道 | 可反复调优（改 prompt、改 catalog），只看这 16 题 |
| `heldout` | 8 道 | D13 只跑一次，不参与调优（用来验证是否过拟合） |
| `None` | 6 道 | 不可回答 + 注入题，不参与准确率统计，所以没有 split |

> 为什么 split 可以是 `None`：3 道不可回答 + 3 道注入题不进准确率分母，split 留空是对的。它们单独算「拒答率 / 拦截率」。

## 二、评测核心概念

### 1. GT SQL（Ground Truth SQL）

GT = Ground Truth（标准答案）。GT SQL = 这道题的标准答案 SQL。评测集每题有一个 `gt_sql`：

```json
{
  "id": "E01",
  "question": "华东大区有哪些门店？列出门店名和城市",
  "gt_sql": "SELECT store_name, city FROM stores WHERE region = '华东'"
}
```

判分流程：
1. `gt_sql` 在库里跑一次 → 得到 `gt`（标准结果集）
2. Agent 生成的 SQL 在库里跑一次 → 得到 `pred`（预测结果集）
3. `pred == gt` → 这题算对

**为什么 D6 要「先验证 GT SQL」**：`gt_sql` 是人写的，可能写错。若它写错（如 `WHERE region = '华东区'` 多了个「区」），模型做对了也会被判错，评测就全废了。所以每道题必须先跑一次。

### 2. pred vs gt

| 变量 | 含义 | 来源 |
|---|---|---|
| `pred` | 模型生成的 SQL 跑出来的结果集 | Agent 的 `exec_result.rows` |
| `gt` | GT SQL 跑出来的结果集 | 评测集 `gt_sql` 在库里执行的结果 |

`pred` = prediction（预测值），`gt` = ground truth（标准答案）。判等核心就一行（`compare.py`，D7 写）：

```python
passed = normalize(pred) == normalize(gt)
```

`normalize` 是 D7 的活，处理浮点容差、列序、NULL 等。

### 3. tags

`tags` 是「这道题考察什么」的标签，纯元数据，不参与判分。作用：

- **D11 badcase 归因**：E03 挂了，看 tag `["join路径", "脏数据:status"]` 就知道是 JOIN 写错还是脏数据没清，不用重读题
- **报告分组统计**：如「脏数据类题通过率 2/3」，靠 tag 分组
- **面试**：被问「你的评测集怎么设计」，翻 tags 就能说「我按 XX 类坑分了标签」

## 三、SQL / 数据库知识点

### 1. DECIMAL 是什么

DECIMAL 是 MySQL 的**精确小数**类型。和 FLOAT/DOUBLE（浮点数）的关键区别：

| 类型 | 存储 | 精度 | 举例 |
|---|---|---|---|
| FLOAT | 二进制浮点 | ❌ 有误差 | `0.1 + 0.2 = 0.30000000000000004` |
| DOUBLE | 二进制浮点 | ❌ 有误差 | 同上 |
| `DECIMAL(12,2)` | 定点十进制 | ✅ 精确 | `0.1 + 0.2 = 0.30`（严格 2 位小数） |

`DECIMAL(12,2)` 的含义：`12` = 总共 12 位数字，`2` = 小数点后 2 位。最大值为 `9999999999.99`（10 位整数 + 2 位小数）。

**为什么金额一定要用 DECIMAL**：
- 银行、财务、电商金额，1 分钱都不能错
- FLOAT 算 100 次可能有 `0.00000001` 的累计误差，账就对不上
- DECIMAL 是字符串式存储，按位计算，结果精确

以本项目 `orders.amount` 为例：

```sql
amount DECIMAL(12,2) NOT NULL COMMENT '订单实付金额'
```

所以 `1283400.50` 存进去是精确的 `1283400.50`，不是 `1283400.4999999`。

**本项目中的 DECIMAL 字段**（grep `DECIMAL` 可见）：
- `orders.amount`：订单实付金额
- `products.price / cost`：售价 / 成本
- `order_items.unit_price / discount`：单价 / 折扣率
- `returns.refund_amount`：退款金额

> ⚠️ D6 发现：MySQL DECIMAL 经 pymysql 返回的是 Python 的 **`Decimal`（不是 float）**。D7 的 `compare.py` 必须 `Decimal → float` 统一后再比较。已有种子题里，E04 的 SUM 返回 `Decimal`，E03 的 COUNT 返回 `int`。

### 2. tolerance（判等容差）

**为什么需要容差**：GT 和模型都算对了，但 Python 里 float 比较会有误差。例如：

```python
>>> 1283400.50 == 1283400.50
True                        # 字面量当然相等
>>> sum([320851.30, 320851.30, 320851.30, 320846.60])
1283400.5000000002          # 多了 .0000000002，不等于 1283400.50
```

原因：Python float 是 64 位二进制浮点，`320851.30` 存不下精确值，只能存近似；加几次误差就累积了。

**在本项目中**：

```sql
SELECT SUM(amount * (1 - COALESCE(discount, 0))) FROM order_items
```

- `amount` 在 MySQL 里是精确 DECIMAL
- 但 pymysql 取出来转 Python 时 `DECIMAL → float`
- float 乘法 + 加法 9000 次，误差累积到 `1e-10` 级

**怎么用**：判等不是 `pred == gt`，而是 `abs(pred - gt) < tolerance`：

```python
assert pred == gt                 # 不用容差：1e-10 误差 → 挂
assert abs(pred - gt) < 1e-6      # 用容差：1e-10 < 1e-6 → 过
```

**量级**：`1e-6 = 0.000001`（百万分之一）。对金额来说，`1283400.50` 与 `1283400.5000001` 差 `0.0000001`，小于 `1e-6`，视为相等。财务场景够用（差 0.0000001 元没意义）。

**判断原则**：

| 题目类型 | tolerance | 理由 |
|---|---|---|
| 纯计数题（`COUNT(*)`） | `0` | 整数没有精度问题，「差 1」就是真错 |
| 金额求和题（含折扣乘法） | `0.01` | 精确到分；9000 行乘法误差可能到 `1e-5` 级，容忍 1 分钱 |
| 比率 / 平均值题 | `1e-6` | 一般够用 |

本项目现状：`tolerance: float = 1e-6` 是默认值，每道题可在 JSONL 里写 `"tolerance": 0.01` 单独覆盖。

### 3. COALESCE 是什么

SQL 函数：`COALESCE(a, b, c, ...)` 返回第一个非 NULL 的值。

```sql
COALESCE(NULL, NULL, 100)   -- 返回 100
COALESCE(0.5, 100)          -- 返回 0.5
COALESCE(NULL, 0)           -- 返回 0（常用：NULL 当 0 处理）
```

本项目用法（`order_items` 金额计算）：

```sql
amount * (1 - COALESCE(discount, 0))
```

**为什么需要它**：
- `discount` 约 30% 是 NULL（D1 seed 埋的脏数据）
- `1 - NULL = NULL`（SQL 的 NULL 传染性）
- 所以 `amount * (1 - NULL) = NULL`，整行金额算不出来
- 用 `COALESCE(discount, 0)`：NULL 当 0（无折扣），`1 - 0 = 1`，整行金额 = amount

**不写 COALESCE 的后果**：30% 的行变 NULL，`SUM` 会忽略它们，总额偏小——这是**口径错的典型**（SQL 能跑、结果看起来对、但业务上错了）。

### 4. TRIM / LOWER 归一化

- `TRIM()` 去首尾空格：`TRIM('  paid  ')` → `'paid'`
- `LOWER()` 转小写：`LOWER('PAID')` → `'paid'`
- 组合 `LOWER(TRIM(o.status)) = 'paid'`：把「任何脏形态的 paid」归一化后统一匹配

| 数据里的值 | `LOWER(TRIM(...))` 后 | 匹配 `'paid'` |
|---|---|---|
| `'paid'` | `'paid'` | ✅ |
| `'PAID'` | `'paid'` | ✅ |
| `'Paid'` | `'paid'` | ✅ |
| `'PAID '`（带空格） | `'paid'` | ✅ |
| `' paid '`（两端空格） | `'paid'` | ✅ |

> 实测：`status='paid'` 只少了 5 条，因为 `ci`（大小写不敏感）让 `'PAID'` 也能匹配，唯一漏网的是带空格的 `'PAID '`——正好是 seed 里埋的 5 条。

### 5. AVG vs SUM/COUNT(*)

数据：`products.price` 120 行，其中 3 个 NULL、117 个非 NULL。

| 写法 | 分子 | 分母 | 结果 |
|---|---|---|---|
| `AVG(price)` | `SUM(price)=292611.83` | `COUNT(price)=117` | 2500.947265 |
| `SUM(price)/COUNT(*)` | `SUM(price)=292611.83` | `COUNT(*)=120` | 2438.423583 |

**关键区别**：`COUNT(price)` 只数非 NULL → 117；`COUNT(*)` 数所有行 → 120。分母差 3，结果差 2.5%。

> **记忆点**：`AVG(x)` 等价于 `SUM(x)/COUNT(x)`，**不是** `SUM(x)/COUNT(*)`。

### 6. 长 SQL 怎么换行

Python 相邻字符串字面量会自动拼接，这是最标准的「长字符串换行」写法：

```python
gt_sql=(
    "select s.city, count(*) as order_count "
    "from orders o join stores s "
    "on o.store_id = s.store_id "
    "where lower(trim(o.status)) = 'paid' "
    "group by s.city"
)
```

上面 5 行等价于下面 1 行：

```python
gt_sql="select s.city, count(*) as order_count from orders o join stores s on o.store_id = s.store_id where lower(trim(o.status)) = 'paid' group by s.city"
```

**比 `"""..."""` 好**：多行字符串会保留换行符，你不想让 SQL 里真的带换行符（虽然 MySQL 不在意，但 JSONL 里会多字节）。

> 小提示：`count(*)` 作列名在生产环境不太好（不同库里大小写可能不同），D7 的 `compare.py` 会处理列名对齐，但写 GT SQL 时显式起别名更干净：`SELECT category, COUNT(*) AS product_count FROM products GROUP BY category`。

### 7. pymysql 报错排查

`TypeError: can't concat tuple to bytes` —— 90% 是 **SQL 本身语法错了**（括号不匹配、引号没闭合、逗号多了），不是 pymysql 的 bug。先检查 SQL 语法。

更稳的排查方式：把 SQL 拿到 MySQL 客户端手动跑一遍，看 MySQL 报什么错——那个错才是真实错。

## 四、Python / Pydantic 知识点

### 1. Literal

Python 的类型注解：表示「这个值只能是列出的几个之一」。

```python
Split = Literal["dev", "heldout"]
```

意思是 `split` 只能是 `"dev"` 或 `"heldout"`，写别的就报错。

**为什么用**：
- 不用 Literal：`split: str = None`——什么字符串都能填，拼错 `"deev"` 也不报错
- 用 Literal：`split: Split = None`——拼错时 IDE 标红、Pydantic 校验直接拒绝

**好处**：评测集 30 条数据，`split` 只能有 2 个值、`layer` 只能 9 个值、`expect` 只能 3 个值——拼错立刻暴露，不会等 D11 评测才发现「这个值我不认识」。

### 2. model_dump_json(indent=2)

Pydantic v2 方法：把 Pydantic 模型对象转成 JSON 字符串。

```python
c = EvalCase(...)                # 一个 EvalCase 对象
c.model_dump_json(indent=2)      # 转成格式化好的 JSON 字符串
```

- `indent=2`：2 个空格缩进（可读性）；不写就是一行压扁的 JSON
- 调试时看对象内容方便
- 评测集冻结时会写 JSONL 文件（每行一个），`model_dump_json()` 就是生产 JSONL 的接口

**对比 `model_dump()`**：`model_dump()` 返回 `dict`（Python 字典），`model_dump_json()` 返回 `str`（JSON 字符串）。写文件用后者。

## 七、refuse vs blocked（精确区别）

两者最终都是 `final_status="refused"`，但路径和能力不同。

| | refuse | blocked |
|---|---|---|
| 模型做了什么 | 返回 `{"action":"refuse"}`，**没生成 SQL** | **生成了 SQL**（危险的） |
| 谁决定拦截 | **模型自己** | **网关** |
| `state["sql"]` | `""` 空串 | 危险 SQL 原文 |
| `failure_reason` | `"NO_SQL"` | `"SQL_BLOCKED"` |

**路径差异**：
- refuse：`generate_sql → route_gen "empty" → refuse`（validate 没被调用）
- blocked：`generate_sql → validate_sql(blocked=True) → route_guard "block" → refuse`

**D7 判分**：
- refuse 题：`final_status=="refused" and sql is None`
- blocked 题：`final_status=="refused" and sql is not None and failure_reason=="SQL_BLOCKED"`

**各自证明的能力**：
- refuse 题 → 模型识别「不可回答」的能力
- blocked 题 → 网关拦截「危险 SQL」的能力

## 九、LLM 扩写审查清单（5 维度，缺一不可）

1. **跑通**：GT SQL 执行无报错
2. **有区分度**：结果非空，且不是「全部行」（必须有过滤效果）
   - ❌ 反例：8 家门店全部超 10 万 → 无区分度
   - ❌ 反例：从未产生的订单 → 空集
3. **layer 对齐**：确实考了该 layer 的考点
   - ❌ 反例：子查询层出了纯 TopN
4. **口径对**：`LOWER(TRIM())` / `COALESCE` / 时间边界
5. **题面无歧义**：一个问法只有一个口径
   - ❌ 反例：「统计其订单数」——「其」指谁？

### 实测：LLM 扩写通过率约 40%

- 子查询层 5 道候选 → 1 道直接可用、1 道改题面可用、3 道淘汰
- **LLM 能写对 SQL**（DeepSeek 对 schema 很熟，`LOWER(TRIM)` 都写对了）
- **但 LLM 判断不了「有没有区分度」、「layer 对不对」、「题有没有歧义」**
- 所以 §4.3 强调「人工逐题执行校验」不是走过场，**每道题 3–5 分钟审查**

## 十、排查纪律（回答要点提炼）

### 「如果结果是 4 行，说明什么？不是 4 行先查什么？」

> 说明 GT SQL 检索出来就是这 4 行。如果不对，**先查近的（SQL），再查远的（数据）**——这是「先验证再入库」的纪律。

**正确排查顺序**：
1. **先看 SQL 本身**：表名对吗？列名 `category` 在 `products` 表里吗？`GROUP BY` 写了吗？（SQL 写错最常见，先排）
2. **再查数据**：`SELECT COUNT(*) FROM products` 是 120 吗？`SELECT DISTINCT category FROM products` 有 4 个值吗？
3. **最后查编码**：`data` 里品类名是中文还是乱码？

> ⚠️ 「先查数据再查语句」是反的——漏了 `GROUP BY` 这类 SQL 错误才是最高频的。

## 十一：最终复盘

1. **LLM扩写的通过率只有40%**：LLM扩写只能保证sql正确，不能判断题目是否有歧义，是否有区分度，需要人审查。
2. **跑通≠能用**：LLM扩写的候选集跑通，但是没有区分度的话，依旧测不出能力
3. **refuse vs blocked 本质区别是“有没有sql被生成”**：refuse是模型没有生成sql就进行拒答，
blocked是模型写了危险的sql之后被本地网关validate_sql拦截，这两者是不同的能力。
