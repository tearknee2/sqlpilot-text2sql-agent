**结论：**
1. **14 道题三组全部 10/10 稳定对** → 模型对 dev 基础题已完全掌握。

3. **E05**：G1/G2 十次全错（稳定失败，模型固定缺陷：多 SELECT `store_id` / 漏 `store_name` 的列选择粒度错误）；G0 3/10（全量表偶见好转，但仍不稳定）。属**静默语义错**，DB 不报错、执行期纠错抓不到。

## 三、消融结论（诚实版）

- **检索（G0 vs G2）**：dev 上无显著差异，G0 平均（93.75%）略高于 G2（91.25%）但属抖动范围。
- **纠错（G1 vs G2）**：dev 上无显著差异；E05/E16 两类错误都**不触发执行期纠错**（E05 是语义错不报错、E16 是抖动），故纠错在 dev 无用武之地。
- **区间重叠声明**：三组 10 次重复的区间存在较大重叠（87.5%~100%）。结合逐题稳定性，目前**没有足够证据证明检索策略或自纠错机制在这 16 道题上带来稳定、明确的准确率提升**。波动可能来自模型生成、SQL 执行、结果比较等多因素，**不将小样本差异夸大为普遍性能优势**。
- **真正信号在"逐题"而非"平均"**——这比单一准确率更有工程价值。

### 按 GPT 分层归因（A/B/C/D 四类）

| 类别 | 含义 | 题号 | 价值 |
|---|---|---|---|
| **A 类：正确触发并挽回** | 首次生成错 SQL → 纠错重试 → 最终成功 | **S02, S09, S10, S22, S29**（5题） | **自纠错能力的直接证明** |
| **B 类：安全拒答** | 题面无同义词/范围外 → 直接拒答，不瞎编 | S01, S03, S04, S05, S06, S27 | 范围外闸门 / 幻觉控制 |
| **C 类：触发但未挽回** | 触发了纠错，但错误类型无法修复（如 MySQL 不支持的函数） | S07, S08, S11, S18, S23, S26 | 纠错边界（模型知识错误救不了） |
| **D 类：正常解答** | 模型一次写对，不触发 | S12-S17, S19-S21, S24, S25, S28, S30 | 模型基础能力 |

> **关键解读**："不触发"不等于系统差——**B 类的拒答（安全边界）和 D 类的一次答对（基础能力）都是正确行为**。
> **纠错的直接证据 = A 类 5 题（触发且挽回，挽回率 45.5%）**；**纠错的边界 = C 类（可触发但不可修复）。**

## 五、Badcase 归因（任务4）

### Badcase 1：E05（各门店已支付销售额 Top3）
- **预测 SQL 问题**：返回 `store_id` 而非 `store_name`（或 GROUP BY 粒度错）。
- **归因**：`WRONG_COLUMN_SELECTION` —— 列选择粒度错误（多选辅助列 / 漏业务列）。
- **根因**：模型倾向多返回主键辅助列，未严格对齐"只要门店名+销售额"的业务语义；属**静默语义错**，DB 不报错、纠错抓不到。
- **稳定性**：G1/G2 10 次全错（稳定缺陷）；G0 3/10（全量表偶见好转，不稳定）。

### Badcase 2：E16（数码买家已支付订单数 Top5）
- **预测 SQL 问题**：排序加了多余 tie-breaker（`o.customer_id ASC`）、`category='数 码'` 偶发空格 → `ordered_mismatch`。
- **归因**：`GENERATION_NONDETERMINISM`（生成抖动）+ `ORDER_SENSITIVITY`（评测器对并列排序敏感）。
- **根因**：不同运行中 SQL 写法、排序细节或输出列顺序存在变化，可能与模型生成波动及结果比较规则（`ORDER BY` 并列值/列对齐）共同有关。**目前尚不能将差异完全归因于模型能力或比较器**，需结合逐次 SQL、执行结果和比较日志进一步分析。
